title: Services and Actions
description: Define modular backend services and typed actions with Effect Schema and Effect handlers.

Services structure backend domains in Brick-TS, while actions provide typed business logic executable both in-process and over HTTP, RPC, and MCP.

## Minimal Example

Define an immutable service, register a typed action with Effect Schema input/output contracts and declared error types, and invoke it either in-process or over HTTP:

```ts title="src/services/users.ts"
import { Brick } from "@brickkit/core";
import { NotFound } from "@brickkit/core/contracts";
import { Effect, Schema } from "effect";

// Mock data store
const users = new Map([
  ["usr_1", { id: "usr_1", name: "Ada Lovelace", email: "ada@example.com" }],
]);

// 1. Declare the action contract
export const GetUser = Brick.action("getUser", "/api/users/getUser", {
  input: Schema.Struct({
    id: Schema.String.check(Schema.isMinLength(1)),
  }),
  output: Schema.Struct({
    id: Schema.String,
    name: Schema.String,
    email: Schema.String,
  }),
  errors: [NotFound],
  description: "Retrieve a user profile by unique ID",
});

// 2. Attach the Effect handler
export const getUser = GetUser(({ id }) => {
  const user = users.get(id);
  if (!user) {
    return Effect.fail(
      new NotFound({ message: `User with ID '${id}' not found` }),
    );
  }
  return Effect.succeed(user);
});

// 3. Group actions into an immutable service
export const usersService = Brick.service("users", {
  actions: { getUser },
});
```

<Callout type="info">
  In Brick-TS, action keys in `Brick.service({actions})` must match the action's
  declared identifier. This guarantees that typed clients, HTTP routes, and RPC
  registrations stay perfectly aligned.
</Callout>

## Services (`Brick.service`)

A service groups cohesive actions into an immutable domain boundary:

```ts title="src/services/orders.ts"
import { Brick } from "@brickkit/core";
import { createOrder, cancelOrder } from "./actions";

export const ordersService = Brick.service("orders", {
  actions: { createOrder, cancelOrder },
});
```

### Service Options Table

| Option    | Type                               | Description                                                                                            |
| :-------- | :--------------------------------- | :----------------------------------------------------------------------------------------------------- |
| `name`    | `string`                           | Unique identifier for the service domain (e.g. `"orders"`). Used in routes, OpenAPI tags, and clients. |
| `actions` | `Record<string, ActionConstraint>` | Object map of action implementations whose keys match action identifiers.                              |

`Brick.service` returns a frozen object containing `{ name, actions, group }`, where `group` is a native Effect `HttpApiGroup`.

## Actions (`Brick.action`)

Actions are the core unit of compute in Brick-TS. Every action is defined with Effect Schema contracts and an Effect handler function.

### Action Configuration Table

| Property      | Type                    | Default      | Description                                                                       |
| :------------ | :---------------------- | :----------- | :-------------------------------------------------------------------------------- |
| `name`        | `string`                | _(Required)_ | Unique identifier for the action within the service (e.g. `"getUser"`).           |
| `path`        | `` `/${string}` ``      | _(Required)_ | HTTP route path (e.g. `"/api/users/getUser"`).                                    |
| `input`       | `Schema.Top`            | _(Required)_ | Effect Schema validating the incoming JSON payload.                               |
| `output`      | `Schema.Top`            | _(Required)_ | Effect Schema validating the returned data.                                       |
| `errors`      | `readonly Schema.Top[]` | _(Required)_ | Array of `Schema.TaggedError` classes declared as possible domain failures.       |
| `description` | `string`                | `undefined`  | Description exported to OpenAPI 3.1 and MCP tool metadata.                        |
| `title`       | `string`                | `undefined`  | Human-readable title exported to OpenAPI and MCP tool metadata.                   |
| `mcp`         | `boolean`               | `false`      | When `true`, exposes the action as a Model Context Protocol tool for AI agents.   |
| `tool`        | `ToolAnnotations`       | `undefined`  | Tool behavior annotations (`readOnly`, `destructive`, `idempotent`, `openWorld`). |

### Monomorphic Execution (In-Process vs HTTP)

An action can be called in-process without network overhead or data serialization:

```ts title="src/example-call.ts"
import { getUser } from "./services/users";
import { Effect } from "effect";

// 1. Direct in-process execution as an Effect:
const program = Effect.gen(function* () {
  const user = yield* getUser({ id: "usr_1" });
  console.log("User name:", user.name); // "Ada Lovelace"
});

await Effect.runPromise(program);
```

When mounted in an application via `Brick.app()`, the HTTP gateway exposes the action as a POST endpoint:

```bash
curl -X POST http://localhost:4000/api/users/getUser \
  -H "Content-Type: application/json" \
  -d '{"id": "usr_1"}'
```

Both invocations run the same steps: input decoding and validation, OpenTelemetry span creation (`brick.action.getUser`), handler execution, and output validation.

## HTTP Endpoints with REST Methods (`Brick.endpoint`)

While `Brick.action` standardizes on JSON POST payloads, `Brick.endpoint` lets you define full REST endpoints with distinct parameter sources:

- `params`: URL path parameters (e.g. `/:id`)
- `query`: URL query string parameters
- `payload`: Request body payload (for POST, PUT, PATCH)
- `headers`: HTTP request headers

```ts title="src/services/users-rest.ts"
import { Brick } from "@brickkit/core";
import { NotFound } from "@brickkit/core/contracts";
import { Effect, Schema } from "effect";

export const deleteUser = Brick.endpoint(
  "deleteUser",
  "DELETE",
  "/api/users/:id",
  {
    input: {
      params: Schema.Struct({ id: Schema.String }),
    },
    output: Schema.Struct({ success: Schema.Literal(true) }),
    errors: [NotFound],
  },
)((input) =>
  Effect.gen(function* () {
    // input.params.id is fully typed and validated
    return { success: true as const };
  }),
);
```

## Low-Level Routes (`Brick.route`)

For health checks, webhooks, or custom streaming endpoints that bypass schema serialization, use `Brick.route`:

```ts title="src/routes/health.ts"
import { Brick } from "@brickkit/core";
import { HttpServerResponse } from "effect/http";
import { Effect } from "effect";

export const healthRoute = Brick.route(
  "GET",
  "/health",
  Effect.sync(() => HttpServerResponse.jsonUnsafe({ status: "ok" })),
);
```

Pass custom routes into `Brick.app({ routes: healthRoute })` to mount them alongside your services.
