title: Validation and Errors
description: Validate inputs and outputs with Effect Schema and declare structured errors with HTTP statuses.
---

Brick-TS enforces strict runtime schema validation using Effect Schema and provides typed error models through `Schema.TaggedError`.

## Minimal Example

Define an action with Effect Schema contracts and declare custom domain errors that map directly to HTTP statuses:

```ts title="src/services/checkout.ts"
import { Brick } from "@brickkit/core";
import { Effect, Schema } from "effect";

// 1. Declare custom domain errors
export class InsufficientFunds extends Schema.TaggedError<InsufficientFunds>()(
  "InsufficientFunds",
  {
    message: Schema.String,
    limit: Schema.Number,
    requested: Schema.Number,
  },
  { httpApiStatus: 400 },
) {}

// 2. Define action contract with declared errors
const ProcessPayment = Brick.action("processPayment", "/api/checkout/pay", {
  input: Schema.Struct({
    orderId: Schema.String.check(Schema.isMinLength(1)),
    amount: Schema.Number.check(Schema.isGreaterThan(0)),
  }),
  output: Schema.Struct({
    transactionId: Schema.String,
    status: Schema.String,
  }),
  errors: [InsufficientFunds],
});

// 3. Implement handler returning typed effects
export const processPayment = ProcessPayment(({ orderId, amount }) =>
  Effect.gen(function* () {
    if (amount > 10000) {
      return yield* Effect.fail(
        new InsufficientFunds({
          message: "Amount exceeds single-transaction limit",
          limit: 10000,
          requested: amount,
        }),
      );
    }

    return {
      transactionId: `tx_${crypto.randomUUID()}`,
      status: "succeeded",
    };
  }),
);

export const checkoutService = Brick.service("checkout", {
  actions: { processPayment },
});
```

## Schema Validation with Effect Schema

Effect Schema provides composable schema combinators that validate payloads at runtime and infer static TypeScript types:

```ts title="src/schemas/user.ts"
import { Schema } from "effect";

export const CreateUserSchema = Schema.Struct({
  name: Schema.String.check(Schema.isMinLength(2), Schema.isMaxLength(100)),
  email: Schema.String.check(Schema.isPattern(/^[^@\s]+@[^@\s]+$/)),
  role: Schema.Literals(["admin", "member"]),
  tags: Schema.optionalKey(Schema.Array(Schema.String)),
});

// Infer static TypeScript type:
export type CreateUserInput = typeof CreateUserSchema.Type;
```

### Boundary Validation

When an HTTP request arrives, Brick decodes the incoming JSON payload against the action's `input` schema before invoking your handler. If validation fails, Brick automatically returns HTTP status 400 with details about the failed schema check. Handlers only ever execute with fully validated, decoded data.

## Tagged Error Classes

Domain errors are defined as subclasses of `Schema.TaggedError`:

```ts title="src/errors.ts"
import { Schema } from "effect";

export class OrderNotFound extends Schema.TaggedError<OrderNotFound>()(
  "OrderNotFound",
  { message: Schema.String, orderId: Schema.String },
  { httpApiStatus: 404 },
) {}
```

The `{ httpApiStatus: 404 }` annotation instructs Brick's HTTP gateway to serialize the error with HTTP status 404. Over the wire, the response body preserves the tagged structure:

```json
{
  "_tag": "OrderNotFound",
  "message": "Order not found",
  "orderId": "ord_123"
}
```

## Standard Built-in Error Classes

`@brickkit/core/contracts` exports standard HTTP error classes for common failure cases:

| Error Class           | Status | Description                                                |
| :-------------------- | :----- | :--------------------------------------------------------- |
| `BadRequest`          | 400    | Malformed request or invalid parameters.                   |
| `Unauthorized`        | 401    | Authentication required or token invalid.                  |
| `Forbidden`           | 403    | Authenticated caller lacks permission.                     |
| `NotFound`            | 404    | Requested resource does not exist.                         |
| `Conflict`            | 409    | Unique constraint violation or conflicting resource state. |
| `InternalServerError` | 500    | Unexpected internal failure or database error.             |

Each built-in error accepts `{ message: string }`:

```ts
import { NotFound } from "@brickkit/core/contracts";

return yield * Effect.fail(new NotFound({ message: "User not found" }));
```

## CRUD Error Classes

`@brickkit/crud` provides standard error types for database operations:

| Error Class       | Status | Description                                         |
| :---------------- | :----- | :-------------------------------------------------- |
| `InvalidInput`    | 400    | Filter operator or mutation field policy violation. |
| `Forbidden`       | 403    | CRUD `authorize` predicate returned `false`.        |
| `NotFound`        | 404    | Primary key not found or row excluded by `scope`.   |
| `Conflict`        | 409    | Unique key or database constraint violation.        |
| `DatabaseFailure` | 500    | Database driver error during query execution.       |

## Typed Failure Handling in Handlers

Because Brick-TS uses Effect, domain errors are tracked in the Effect's error channel (`E`). You can catch, map, and transform errors with full compiler assistance:

```ts
import { Effect } from "effect";
import { NotFound, Conflict } from "@brickkit/core/contracts";

const program = findRecord.pipe(
  Effect.catchTag("NotFound", (err) =>
    Effect.fail(new Conflict({ message: `Cannot proceed: ${err.message}` })),
  ),
);
```

If a handler attempts to return an error class that was not declared in the action's `errors` array, **TypeScript will raise a compilation error**.
