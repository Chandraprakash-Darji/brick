---
title: Typed Client
description: Automatically generated browser-safe types and routes from your Brick app
---

The typed client provides autocomplete and compile-time input/output checking.
The Vite plugin derives its contract from your app's registered services, so
you define actions once and never maintain a second action list.

## Export your app

Any entry filename works; its default export must be a `BrickApp`. Use
`brick({ services })` directly. The entry constructs the app without calling
`.listen()`:

```ts
// src/api/app.ts
import { brick } from "@brickkit/core";
import { records, users } from "./services";

export default brick({ prefix: "/v2", services: [records, users] });
```

## Add the Vite plugin

```ts
import { defineConfig } from "vite";
import { brickClient } from "@brickkit/cli/vite";

export default defineConfig({
  plugins: [
    brickClient({ entry: "./src/api/app.ts" }),
    // Your framework plugins follow.
  ],
});
```

The plugin generates `_brick/contract.ts` at development startup, before the
frontend loads, and during production builds. It reads the app's selected
services and prefix. Changes to the app or its dependencies regenerate the
contract, and Vite reloads its frontend consumers. Unchanged metadata leaves
the generated file untouched, avoiding update loops.

Add `_brick/` to `.gitignore`. Set `output` in the plugin options if you need
another location. Generation evaluates the app entry, so configuration needed
to construct the app must be available at startup and build time. This plugin
uses Vite 8; no separate code-generation command is needed.
Keep startup jobs and connection-opening initialization outside the app
definition module, for example in request handlers or the server bootstrap.

## Generate without Vite

For another frontend framework or build tool, use the standalone Bun CLI with
the same default-exported app:

```sh
brick gen client src/api/app.ts
# Or choose an output location:
brick gen client src/api/app.ts --output frontend/src/contract.ts
```

The default output is `_brick/contract.ts` relative to the working directory.
Vite is not required. Run generation before your frontend development server,
production build, or type check, and rerun after backend definition edits.
For example, add `"gen:client": "brick gen client src/api/app.ts"` to your
package scripts and run `bun run gen:client` before your frontend command.
The CLI uses the app's selected services and prefix, creates missing output
directories, and skips rewriting unchanged contents. The same entry-evaluation
and schema requirements described above apply.

## Call your API

```ts
// src/lib/api.ts
import { createBrickClient } from "@brickkit/core/client";
import { contract } from "../../_brick/contract";

export const api = createBrickClient({
  baseUrl: "http://localhost:8085",
  contract,
});

await api.records.get_value({ doctype: "CRMDeal", fields: ["name"] });
// For the action path /v2/records/:doctype/value and method POST:
// POST /v2/records/CRMDeal/value with { fields: ["name"] }
```

The client infers its types directly from the generated contract. The file
contains transport types and route metadata, with no runtime imports, backend
handlers, service instances, or database code. It also exports `AppContract`
when you need to refer to the complete contract type explicitly.

Custom HTTP actions are grouped by service name; dotted names become nested
namespaces. Resources use their names at the root (`api.page.create`,
`api.page.list`, etc.) with their normal REST methods. MCP-only tools are absent;
opt in with `http: true` or `service.action(tool)` to expose them over HTTP.
Raw endpoints are outside the generated action client.

Schemas determine JSON transport types. Absent input/output schemas yield
`unknown`; unresolved schema references and non-JSON transport types fail
explicitly. Missing path parameters reject before sending a request. Parameter
names follow the server's full-segment syntax, and values are URL-encoded.

## Embedded servers such as TanStack Start

The same app runs inside your framework server. Import it through Vite's
server-only module and forward the API requests your app owns:

```ts
import app from "virtual:brick-app";

export function handleBrickRequest(request: Request) {
  return app.fetch(request);
}
```

Add `/// <reference types="@brickkit/cli/vite/client" />` to `vite-env.d.ts` for
its type declaration. The module tracks the app and its dependencies for hot
reload and rejects browser imports. The Pages example keeps one TanStack Start
app, with no separate API listener; its existing server entry forwards Brick
paths and lets Start handle SSR and assets.

### Errors

One throw-based convention, mirroring local `action.execute` semantics (promises can't encode thrown types, so declared codes surface on the error object, not in the return type):

```ts
import {
  ActionExecutionError,
  ValidationError,
  BrickTransportError,
  BrickServerError,
} from "@brickkit/core/client";

try {
  await api.page.create(input);
} catch (err) {
  if (err instanceof ActionExecutionError) {
    err.code; // The declared server error code.
  } else if (err instanceof ValidationError) {
    err.errors; // [{ path, message }] — same shape as local execution
  } else if (err instanceof BrickServerError) {
    err.status; // unexpected 5xx outside the declared contract
  } else if (err instanceof BrickTransportError) {
    err.status; // network failure or contract-external 4xx
  } else if (err instanceof DOMException && err.name === "AbortError") {
    // cancellation propagates unwrapped
  }
}
```

`InferActionErrorCodes<AppContract["page"]["create"]>` gives the declared code union for a generated action when you need it in a type position.

### Options

```ts
const api = createBrickClient({
  baseUrl: "http://localhost:4000",
  contract,
  headers: () => ({ authorization: `Bearer ${getToken()}` }),
  timeoutMs: 5000,
  fetch: customFetch,
});

await api.page.list(
  { limit: 10 },
  { signal, headers: { "x-trace-id": "tr_1" } },
);
```

The generated contract already includes the app's prefix. Without a runtime
contract, the low-level client's conventional resource/action routes remain
available, but custom paths cannot be inferred from types alone.
