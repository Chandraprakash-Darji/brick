---
title: Access Control and Policies
description: Secure actions and CRUD operations with role-based authorization and row scoping.
---

Brick-TS provides two complementary layers of access control: operation-level authorization in actions and row-level scoping on CRUD resources.

## Action Authorization

Actions enforce authorization within their Effect pipeline. By requiring authentication dependencies in the Effect environment, actions ensure that unauthorized requests reject before business logic executes:

```ts title="src/services/articles.ts"
import { Brick } from "@brickkit/core";
import { Forbidden, Unauthorized } from "@brickkit/core/contracts";
import { Context, Effect, Schema } from "effect";

export interface User {
  id: string;
  role: "reader" | "editor" | "admin";
}

export class CurrentUser extends Context.Service<CurrentUser, User>()(
  "CurrentUser",
) {}

export const PublishArticle = Brick.action(
  "publishArticle",
  "/api/articles/publish",
  {
    input: Schema.Struct({ articleId: Schema.String }),
    output: Schema.Struct({ published: Schema.Boolean }),
    errors: [Unauthorized, Forbidden],
  },
);

export const publishArticle = PublishArticle(({ articleId }) =>
  Effect.gen(function* () {
    const user = yield* CurrentUser;

    // Check permissions
    if (user.role !== "editor" && user.role !== "admin") {
      return yield* Effect.fail(
        new Forbidden({
          message: "Only editors or admins can publish articles",
        }),
      );
    }

    return { published: true };
  }),
);
```

If `CurrentUser` cannot be resolved (for instance, if the request lacks a valid token), the authentication layer fails with `Unauthorized` (HTTP 401). If the user is authenticated but lacks required permissions, the action fails with `Forbidden` (HTTP 403).

## CRUD Access Policies

CRUD resources from `@brickkit/crud` are **deny-by-default**. `access` is a required option when implementing a contract. An access configuration without `authorize` rejects every operation with `Forbidden` (403).

### 1. Public Access

Allow unrestricted access across all CRUD operations:

```ts title="src/services/catalog.ts"
export const catalogActions = catalogContract.implement({
  store: sqliteStore(catalogTable, CatalogDb),
  access: "public",
});
```

### 2. Operation-Level Authorization (`authorize`)

The `authorize` callback runs before database queries are executed. It receives `{ operation, input }` and returns an `Effect` resolving to a boolean:

```ts title="src/services/documents.ts"
import { crudContract, sqliteStore } from "@brickkit/crud";
import { Unauthorized, Forbidden } from "@brickkit/core/contracts";
import { CurrentUser } from "../auth";
import { Effect } from "effect";

export const docActions = docContract.implement({
  store: sqliteStore(documentsTable, DocDb),
  access: {
    authorize: ({ operation }) =>
      Effect.gen(function* () {
        const user = yield* CurrentUser;
        // Admins can perform any operation
        if (user.role === "admin") return true;
        // Members can read, but cannot delete
        if (operation === "delete") return false;
        return true;
      }),
  },
});
```

If `authorize` returns `false`, `@brickkit/crud` rejects the request with `Forbidden` (HTTP 403).

### 3. Row-Level Scoping (`scope`)

The `scope` callback generates a Drizzle SQL expression that restricts which rows an operation can read, update, or delete:

```ts title="src/services/pages.ts"
import { crudContract, sqliteStore } from "@brickkit/crud";
import { Unauthorized } from "@brickkit/core/contracts";
import { pagesTable } from "./schema";
import { PagesDb } from "./db";
import { CurrentUser } from "../auth";
import { eq } from "drizzle-orm";
import { Effect } from "effect";

export const pageActions = pageContract.implement({
  store: sqliteStore(pagesTable, PagesDb),
  access: {
    authorize: () =>
      Effect.gen(function* () {
        const user = yield* CurrentUser;
        return Boolean(user.id);
      }),
    scope: ({ operation }) =>
      Effect.gen(function* () {
        // Create operations do not filter existing rows
        if (operation === "create") return undefined;

        const user = yield* CurrentUser;
        // Restrict all queries to rows where userId matches the authenticated user
        return eq(pagesTable.userId, user.id);
      }),
  },
  hooks: {
    // Automatically attach authenticated user ID on creation
    beforeCreate: ({ data }) =>
      Effect.gen(function* () {
        const user = yield* CurrentUser;
        return {
          ...data,
          id: crypto.randomUUID(),
          userId: user.id,
        };
      }),
  },
});
```

### How Scoping Works at Runtime

When a user calls `page.list`, `page.get`, `page.update`, or `page.delete`:

1. `authorize` runs. If it fails or returns `false`, execution halts immediately.
2. `scope` runs and produces a SQL predicate: `pagesTable.userId = 'usr_42'`.
3. `@brickkit/crud` combines the scope predicate with any client-supplied filter criteria using SQL `AND`:
   ```sql
   WHERE (pages.user_id = 'usr_42') AND (pages.title LIKE '%Guide%')
   ```
4. Even if a malicious caller supplies `id: "page_owned_by_someone_else"` to `page.get` or `page.delete`, the scoped query returns zero rows, resulting in `NotFound` (404). Data cannot leak across tenant boundaries.
