title: Extensions

brick-ts has no plugin interface and no `app.Use()`. You extend a service by
composing the primitives below — all TypeScript, in your own service files.

## Extension points

| Extension point | API | Use it for |
|-----------------|-----|------------|
| Resource hooks | `beforeCreate` / `afterCreate` / `beforeUpdate` / `afterUpdate` / `beforeDelete` / `afterDelete` on `service.resource()` | Audit trails, slug validation, denormalized counters |
| Custom actions | `service.action()` with optional `path` / `method` | Domain operations that are not CRUD (publish, render, invite) |
| Raw endpoints | `app.endpoint({ method, path, handler, service, database, summary, description, tags })` | HTML pages, webhooks, MCP transports — anything outside the JSON action mesh |
| Service proxy | `createServiceProxy()` | Call another service's actions with typed dispatch |
| Built-in capabilities | `createBrickServer()` options | Request logging, Scalar / Swagger docs, OpenAPI, health, architecture export |

## Endpoint context

Raw endpoint handlers receive an `EndpointContext`:

```ts
interface EndpointContext {
  params: Record<string, string>;
  query: Record<string, string | undefined>;
  body: unknown;
  headers: Record<string, string>;
  request: Request;
  set: { status?: number; headers: Record<string, string> };
  db: any; // Drizzle db from `service` (or first service with one)
  logger: { info: (...a: any[]) => void; warn: (...a: any[]) => void; error: (...a: any[]) => void; debug: (...a: any[]) => void };
  traceId: string;
  requestId: string;
}
```

Errors map the same way as the action mesh: throwing `ValidationError` or
`ActionExecutionError` (or any error with a numeric `status`) sets the HTTP
status; anything else becomes a 500.
