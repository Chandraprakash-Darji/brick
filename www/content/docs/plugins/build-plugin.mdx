title: Authoring Plugins
description: Build plugins with definePlugin, a checked manifest and owned tables, lifecycle and host hooks.
---

A plugin packages a capability so that one line installs it: `page.use(comments())`. Write it with `definePlugin`. It has a manifest that Brick checks when the plugin is installed, and one place for each thing the plugin brings: tables, events, routes, hooks into the host's CRUD writes, and an app-wide part with a start/stop lifecycle.

`defineServicePlugin` and `defineResourcePlugin` still work. They are covered [at the end of this page](#the-older-defineserviceplugin-and-defineresourceplugin).

## A complete plugin

```ts title="@acme/brick-comments/src/index.ts"
import {
  ActionExecutionError,
  definePlugin,
  defineSecret,
  eq,
  t,
} from "@brickkit/core";
import { crud } from "@brickkit/crud";

export const comments = definePlugin({
  name: "@acme/brick-comments",
  description: "Comments on any resource.",
  brick: "^0.11.0", // checked when the plugin is installed
  requires: ["@brickkit/crud"], // must be installed on the same host first
  options: t.Object({
    maxLength: t.Integer({ default: 2000, description: "Longest comment." }),
  }),
  secrets: {
    moderationKey: defineSecret("ACME_MODERATION_KEY", { default: "" }),
  },

  // Tables the plugin owns: created in the host service's database, for its engine.
  tables: ({ table, text, timestamp }) => ({
    comments: table("comments", {
      id: text("id")
        .primaryKey()
        .$defaultFn(() => crypto.randomUUID()),
      targetId: text("target_id").notNull(),
      body: text("body").notNull(),
      createdAt: timestamp("created_at")
        .notNull()
        .$defaultFn(() => new Date()),
    }),
  }),
  // Joins the host's event catalog as `comments.added`.
  events: { added: t.Object({ id: t.String(), targetId: t.String() }) },

  // Installed with resource.use().
  resource: ({ resource, service, tables, options, events, hooks }) => {
    // The host's own CRUD writes, inside their transaction.
    hooks.afterDelete(({ id, tx }) =>
      tx
        .delete(tables.comments)
        .where(eq(tables.comments.targetId, String(id))),
    );
    const comment = service
      .resource({
        name: `${resource.name}Comment`,
        table: tables.comments,
        id: tables.comments.id,
      })
      .use(
        crud({
          access: "public",
          fields: {
            id: { read: true },
            targetId: { read: true, create: true, filter: ["eq"] },
            body: { read: true, create: true },
          },
          hooks: {
            beforeCreate: ({ data }) => {
              if (String(data.body).length > options.maxLength)
                throw new ActionExecutionError(
                  "BAD_REQUEST",
                  "Comment is too long",
                  400,
                );
            },
          },
        }),
      );
    return { comments: comment };
  },

  // The app-wide part: lifecycle, middleware and listeners.
  app: ({ on }) => {
    on("start", async ({ secrets }) => {
      /* open a client with secrets.moderationKey.require() */
    });
    on("stop", async () => {
      /* close it */
    });
  },

  dashboard: "./dashboard.js", // a dashboard extension, relative to this file
});
```

```ts title="src/services/pages/page.resource.ts"
import { crud } from "@brickkit/crud";
import { comments } from "@acme/brick-comments";

export const page = pages
  .resource({ name: "page", table: pagesTable, id: pagesTable.id })
  .use(crud({ access: "public", fields: { id: { read: true } } }))
  .use(comments({ maxLength: 500 }));

page.comments; // the pageComment resource, typed
```

`definePlugin` returns a factory. Calling it (`comments({ maxLength: 500 })`) checks the Brick version and the options and returns an instance to install.

## Where it is installed

Scope comes from the install site:

| Install                          | Runs            | Gets                                                     |
| -------------------------------- | --------------- | -------------------------------------------------------- |
| `resource.use(plugin())`         | `resource` part | `resource`, `service`, `tables`, `hooks` of the resource |
| `service.use(plugin())`          | `service` part  | `service`, `tables`, `hooks` of every resource           |
| `brick({ plugins: [plugin()] })` | `app` part only | lifecycle, middleware, listeners                         |

The `app` part also runs for a plugin installed on a service or resource, once per instance, when `brick()` creates the app. A plugin that has no part for a host refuses it: `@acme/brick-comments cannot be installed on a service; use resource.use()`.

## The manifest

| Field       | What Brick does with it                                                                                                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`      | The npm package name. Labels the plugin's routes, tables and events in OpenAPI and the dashboard.                                                                                         |
| `brick`     | A semver range checked against the running `@brickkit/core`: `@acme/brick-comments supports Brick ^0.11.0; this app runs 0.12.1`.                                                         |
| `requires`  | Plugin names that must already be installed on the same host: `@acme/brick-comments requires @brickkit/crud, installed on resource "page" before it`.                                     |
| `options`   | A TypeBox schema. Defaults fill what the user leaves out; the values are checked at install, with errors that name the plugin and the option. The factory's parameter type comes from it. |
| `secrets`   | Secrets from `defineSecret`, so `brick()` checks them at boot and the dashboard and `brick lint` list what the plugin needs.                                                              |
| `tables`    | Tables the plugin owns. See below.                                                                                                                                                        |
| `events`    | Events the plugin emits. They join the host's catalog as `<plugin>.<event>`.                                                                                                              |
| `dashboard` | A dashboard extension module that `brick dev` merges with the app's own.                                                                                                                  |

## Owned tables

`tables` receives engine-aware builders: `table`, `text`, `integer`, `real`, `boolean`, `timestamp` (a `Date`) and `json`. Brick passes the SQLite or the Postgres ones to match the host database, so one plugin works on both.

- **Names.** Each table is prefixed with the host and the plugin: `table("comments")` on resource `page` becomes `page_comments`; a table with another name becomes `page_comments_<name>`. The installer can choose the prefix instead: `comments({}, { prefix: "blog_" })` gives `blog_comments`. A name the service already has is refused.
- **Database.** The tables are added to the host service's database (`database.tables`), so they belong to that service.
- **Schema sync.** `syncSchema(service)` and `syncSchema(database.tables, db)` create them with the app's own tables.
- **Migrations.** Drizzle Kit reads tables from a schema file. Import the services, which installs the plugins, and export the plugin tables by name. Run Drizzle Kit with Bun so it can load `@brickkit/core`:

```ts title="src/schema/plugins.ts"
import { database } from "../services/pages/database";
import "../services/pages/page.resource"; // installs the comments plugin

export const { page_comments } = database.tables;
```

```bash
bunx --bun drizzle-kit generate
```

The file you import must not use top-level `await`, which Drizzle Kit cannot load.

## Host hooks

`hooks.beforeCreate`, `afterCreate`, `beforeUpdate`, `afterUpdate`, `beforeDelete`, `afterDelete` and `afterCommit` subscribe to the host's CRUD writes (resources with `crud()`). They run after the host's own `crud()` hooks, inside the write's transaction, and receive it as `tx`: write through `tx` and the rows commit or roll back with the write. A hook that throws rolls the whole write back. `afterCommit` runs after the commit. On a service, the hooks see the writes of every resource in it. Declare `requires: ["@brickkit/crud"]` so the user installs crud first.

## Lifecycle, middleware and listeners

The `app` part receives `on`, `middleware` and `listeners`:

- `on("start", fn)` runs when the app starts, in install order; `on("stop", fn)` when it stops, in reverse order. Both may be async. `brick dev`, `brick start`, `brick worker` and a built server start the app before serving; `app.listen()` starts it too, and `app.stop()` stops it. In a test, `await app.start()` and `await app.stop()`. A start that throws stops the plugins already started and fails the start.
- `middleware(fn)` runs before every request is routed. Return a `Response` to answer it; return nothing to let it through.
- `listeners(...)` adds event listeners to the app's `events`.

Setup stays synchronous. Open connections in `on("start")`, never while the plugin installs.

## Events

`events: { added: t.Object({ ... }) }` adds `comments.added` to the host service's catalog. In the parts, `events.added` is the event reference, recorded as `<service>.comments.added`. Emit it with `emitEvent(ctx, events.added, payload, { tx })`; listeners take it with `defineListener({ on: events.added })`. Emitting needs `brick({ events })` and an outbox, so a plugin that should work without them checks `service.recorder` first.

## Dashboard extension

`dashboard: "./dashboard.js"` points at a module whose default export is `defineDashboard({ ... })` (see [Dashboard extensions](/docs/dashboard-extensions)). The path is relative to the file that calls `definePlugin`. `brick dev` builds each plugin's extension apart from the app's and merges them: the app's comes first and keeps its slots, a page whose id is taken is skipped, and a plugin's pages without a place go under a section named after the plugin. One that fails to build or load is reported and the others still show.

## What users see

Every route, table and event a plugin contributes is labelled with its name: `x-brick-plugin` in OpenAPI, the plugin beside each route, table and event on the dashboard's overview, and `app.definition.plugins` lists every installation.

## Local plugins

A plugin that is not published lives in `src/plugins/<name>/` with the same layout as a package. Lint it with the `plugin` preset of [`brick lint`](/docs/brick-cli/lint). To publish one, see the [plugin directory](/docs/plugins/directory).

## The older `defineServicePlugin` and `defineResourcePlugin`

Both keep working. They have no manifest, tables, hooks or lifecycle: a `setup` that registers routes and returns an API.

```ts title="src/plugins/greeting.ts"
import { defineServicePlugin, t } from "@brickkit/core";

export const greeting = (salutation = "Hello") =>
  defineServicePlugin({
    name: "example/greeting",
    setup({ routes }) {
      const hello = routes.action({
        name: "hello",
        method: "GET",
        path: "/hello", // GET /api/<service>/hello
        input: t.Object({ name: t.String({ minLength: 1 }) }),
        output: t.String(),
        execute: ({ input }) => `${salutation}, ${input.name}!`,
      });
      return { hello };
    },
  });

export const api = greeterService.use(greeting("Welcome"));
```

`routes` is the same registrar `definePlugin` parts get. Route paths are relative to the route's `scope`: service routes default to `service` (`${prefix}/${service}`), resource routes to `resource` (`${prefix}/${service}/${resource}`), and `app` mounts under `${prefix}`. See [URL Scheme](/docs/routes#plugin-route-scopes). `routes.endpoint()` registers a raw HTTP endpoint outside the JSON action mesh.
